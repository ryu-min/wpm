# Design

## Context

Актуализировано 16 ноября 2026 в рамках [remove-dictation](../remove-dictation/proposal.md). Выполненные этапы переноса, команды и фактические результаты сохранены в [tasks.md](tasks.md). Ниже описаны действующие архитектурные решения после удаления аудиомодуля; прежние операции интеграции не нужно повторять.

Исходная интеграция добавила прямые архитектурные тесты и описание. Последующие modularize-application-boundaries и organize-integration-test-suites выделили модули и группы тестов; действующая delta учитывает их окончательную структуру. Сохраняется один бинарный crate.

## Goals / Non-Goals

**Goals:** согласованная карта обязанностей, точные читаемые правила в тестах и полезная диагностика запрещённых связей.

**Non-Goals:** повторный merge upstream, собственный policy loader, полный анализ компилятора, автоматическое перечисление всех файлов или новый механизм подавления предупреждений.

## Decisions

### Основная карта и правила

Использовать пять модулей исполнения: app, ui, domain, storage и dataset. Main отвечает за терминальный lifecycle и объявления; межмодульные тесты находятся отдельно в src/tests и подключаются только при cfg(test).

```text
main --> app
app --> ui, domain, storage
ui --> domain
storage --> domain, dataset
build.rs --> dataset
```

Структурные объявления модулей и зависимости внутри своего корня разрешены. У domain и dataset нет связей с другими модулями приложения; storage адаптирует формат наборов к domain. App координирует компоненты и владеет сессией, UI рисует её без дублирования счётчиков. Аудиокорень и его разрешения удаляются по remove-dictation.

Точные разрешения внешних crates задаются прямыми именованными тестами по ответственности модулей. Общий dataset читается сборкой и приложением; проверять оба контекста. Межмодульные тесты не расширяют разрешения производственного кода. Корневой ARCHITECTURE.md содержит только ссылки на основную спецификацию и каталог правил.

### Обычная тестовая цель и честные пределы анализа

main.rs набора подключает internal_dependencies, external_dependencies и source_layout. Не добавлять отдельный policy/parser/framework или explicit [[test]]. Анализатор объединяет cfg-ветви, не раскрывает сгенерированный include-код и не доказывает разрешение имён, алиасов Cargo или полноту инвентаря. Непустые селекторы и проверка негативных примеров защищают от молчаливого выпадения правил.

### Приёмка

Проверять единственную цель `architecture`, именованные правила внутренних/внешних зависимостей и размещения исходников. Негативные проверки выполняются в временной копии и должны достигать конкретного архитектурного правила, а не только ошибки компиляции: UI→storage, app→dataset, неправильная ссылка нового вложенного исходника и обнаруженный исходник вне разрешённых корней. Сохранить запрет маркера подавления анализа.

`cargo test --locked --test architecture` и `cargo test --locked --all-features --all-targets` выполняют набор; терминальные сценарии запускаются через `cargo test --locked --test e2e` на Unix с изолированным `WPM_DATA_DIR`. Windows-сборка не является PTY-приёмкой. Нет необходимости в аудиодвойнике или проверке слышимости удалённого режима.

## Risks / Trade-offs

- Старый активный change может вернуть устаревшую карту → delta скопирована полными блоками из согласованного конечного контракта.
- Синтаксическая проверка не доказывает смысл распределения обязанностей → сохранять ревью API и регрессионные сценарии.
- Перенос тестов может скрыть отсутствие цели → проверять Cargo discovery и непустой список правил.

## Migration Plan

Историческая интеграция выполнена и не повторяется. При будущем sync действующая delta обновляет только опубликованные требования по их именам; она не возвращает отменённый audio. Текущие кодовые изменения и проверки идут по remove-dictation. Архивирование и изменение пользовательских данных не требуются.
