# Технический дизайн

## Контекст и границы

Мотивация и область изменения описаны в `proposal.md`. Сейчас Cargo автоматически обнаруживает тринадцать интеграционных целей: `architecture`, `dataset_format` и одиннадцать `e2e_*`. В них находятся 18 архитектурных и 62 терминальных теста. Каждый E2E-файл отдельно подключает `common`; архитектурные правила собраны в одном `main.rs`. Приложение уже разделено на шесть модулей; его архитектурные разрешения и пользовательское поведение при этой работе сохраняются.

Изменение касается организации существующих тестов, их обнаружения и документации запуска. Оно не вводит тестовый фреймворк, новые зависимости, производственные API или дополнительные поведенческие сценарии. Наличие незакоммиченной предыдущей реализации требует ограничить правки текущим переносом и не восстанавливать старые исходники.

## Решения

### 1. По одной цели Cargo для каждого набора

Используется обычное обнаружение `tests/<набор>/main.rs`, без `[[test]]` и без изменения CI:

```text
tests/
├── e2e/
│   ├── main.rs
│   ├── common/mod.rs
│   ├── menu.rs
│   ├── mode_select.rs
│   ├── settings.rs
│   ├── typing.rs
│   ├── result.rs
│   ├── layout_policy.rs
│   ├── spanish_settings.rs
│   ├── spanish_translation.rs
│   ├── spanish_dictation.rs
│   ├── spanish_catalog.rs
│   └── dataset_profiles.rs
├── architecture/
│   ├── main.rs
│   ├── internal_dependencies.rs
│   ├── external_dependencies.rs
│   └── source_layout.rs
└── dataset_format.rs
```

Имена функций тестов сохраняются. Меняются только полные имена: например, функция из прежней цели `e2e_menu` получает префикс `menu::` внутри цели `e2e`. После переноса Cargo должен видеть ровно три интеграционные цели: `e2e`, `architecture`, `dataset_format`. Старые корневые файлы `e2e_*.rs` удаляются, иначе будут собираться дублирующие цели. `dataset_format` остаётся самостоятельной межплатформенной проверкой.

Альтернатива — сохранить одиннадцать целей через явные `[[test]]`. Она усложняет конфигурацию и не даёт единого запуска набора, поэтому не выбрана.

### 2. Один общий модуль E2E и прежняя изоляция

`tests/e2e/main.rs` содержит ограничение `#![cfg(unix)]`, единственное объявление `mod common` и объявления одиннадцати модулей сценариев. Сценарии используют `crate::common`, включая существующие квалифицированные обращения. Отдельное объявление `common` внутри каждого сценария не сохраняется: общий модуль должен иметь один экземпляр статического счётчика и одну идентичность типов в пределах тестового процесса. Перенос не меняет генерацию каталогов по PID, времени и счётчику и не утверждает наличие коллизий в прежней схеме.

PTY-вызов `script`, особенности его аргументов на Unix-платформах, `TestDataDir`, поддельный аудиопроцесс и его управляющие файлы переносятся без изменения поведения. `WPM_DATA_DIR` и другие переменные задаются дочерним командам; глобальное окружение и рабочий каталог тестового процесса менять не требуется. Значение `env!("CARGO_BIN_EXE_wpm")` сохраняется: имя бинарного приложения не зависит от имени интеграционной цели.

В `dataset_profiles.rs` относительный `#[path]` к общему модулю меняется с `../src/dataset/mod.rs` на `../../src/dataset/mod.rs`. В `tests/dataset_format.rs` прежний путь остаётся корректным. Пути к `resources/datasets` не меняются, поскольку Cargo запускает тесты из корня пакета, а не из каталога исходного файла.

### 3. Архитектурные правила разделяются по назначению

`internal_dependencies.rs` получает восемь правил внутренних зависимостей, `external_dependencies.rs` — восемь правил внешних зависимостей, `source_layout.rs` — два правила размещения исходников и запрета подавления анализа. `main.rs` только подключает эти модули и при необходимости кратко объясняет структуру.

Каждый файл содержит обычные читаемые именованные тесты и необходимые импорты. Селекторы, разрешения, сообщения и утверждения сохраняются. Собственная система регистрации правил, парсер спецификаций или общий механизм вычисления политик не нужны. Альтернатива — деление по каждому модулю приложения — создаёт больше мелких файлов и смешивает разные классы правил; выбранное деление соответствует уже существующим группам.

### 4. Выбор набора, группы и отдельного теста

Полный набор запускается через `cargo test --locked --test e2e`, архитектура — через `cargo test --locked --test architecture`. Группу можно выбрать, например, командой `cargo test --locked --test e2e spanish_dictation::` или `cargo test --locked --test architecture internal_dependencies::`.

Фильтр Cargo ищет подстроку: `settings::` также совпадает с `spanish_settings::`. Для однозначного выбора одного теста используется полное имя из `-- --list` вместе с `-- --exact`; простое одинаковое имя функции в разных модулях допустимо. Старые команды `--test e2e_*` перестают выбирать цели и заменяются актуальными примерами в действующих инструкциях.

### 5. Параллельность сохраняется и проверяется

Объединение исполняемых файлов позволяет тестам разных прежних целей выполняться одновременно внутри одного процесса. Изолированные каталоги и переменные дочерних команд остаются основой независимости сценариев. Одновременная нагрузка от PTY, Python и аудиозаглушек может изменить длительность и устойчивость ожиданий; ускорение не обещается.

Приёмка выполняется с обычным числом потоков тестового стенда, без общей блокировки и без `--test-threads=1`. При сбое сначала проверяются изоляция ресурсов и ожидание готовности, фиксируется воспроизводимая причина. Ослабление утверждений, отключение сценариев и общая сериализация не считаются исправлением переноса. Существенное изменение синхронизации требует отдельного зафиксированного решения, а не скрытого расширения этой механической реорганизации.

### 6. Актуальные ссылки и долговременное описание

Delta `repository-architecture` меняет источник точных правил на каталог `tests/architecture/` и описывает точки входа обоих наборов. В предусмотренную реализацию включена явная синхронизация только этой delta в основную спецификацию, без архивирования. Корневой `ARCHITECTURE.md` остаётся коротким указателем: ссылка на описание, каталог правил и при необходимости его точку входа.

В проектной части `AGENTS.md` заменяются пути к E2E и helpers и уточняются команды и фильтры. Личные инструкции не добавляются. Команда CI `cargo test --locked --all-features --all-targets` уже охватывает новые цели. Общий путь `tests/` в `config.context` остаётся правильным, поэтому изменение конфигурации не требуется; допустимо только фактическое уточнение размещения тестов, если оно понадобится, без изменения политики языка и процесса.

Исторические результаты, завершённый план предыдущей модульной реорганизации и другие активные изменения не переписываются. Будущие тесты, включая запланированный испанский набор café, должны следовать новой структуре `tests/e2e/`; упоминание старого будущего имени в чужом плане не является поводом редактировать тот change в этой работе.

## Порядок переноса и проверки

До правок реализации фиксируются списки и количества обнаруживаемых тестов: 62 E2E и 18 архитектурных. После переноса сравниваются полные имена с ожидаемой заменой цели на префикс модуля; каждый прежний тест должен иметь ровно одного преемника. Числа относятся к приёмке этого переноса и не ограничивают добавление будущих тестов.

Сначала переносятся E2E и проверяется новая цель, затем разделяются архитектурные правила и проверяются все 18 тестов. После обновления документации и синхронизации выполняются строгая проверка OpenSpec, проверка отсутствия ошибок форматирования diff и полный `cargo test --locked --all-features --all-targets`. Результаты и длительность фиксируются в задачах. На Windows пустая цель E2E ожидаема и не заменяет Unix-приёмку.

Если локальный macOS SDK воспроизводит уже известную ошибку линковки, допустим прежний локальный префикс `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX15.4.sdk`; он записывается в результатах и не переносится в конфигурацию проекта. Откат касается только переносов этого изменения, без отмены других незакоммиченных работ.
